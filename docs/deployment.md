# Deploying the POS

The POS is one Node process: Express serves `/api/v1`, the built SPA at `/`, and the guest table
menu at `/t/<number>`. It needs two things — a MongoDB Atlas cluster it owns, and a host that runs
`backend/src/server.js`. This document covers Render + Atlas via [`render.yaml`](../render.yaml).

Nothing here connects to the website or its admin panel; they are deployed separately and keep
their own Postgres database.

## 1. MongoDB Atlas

1. Create a free M0 cluster (choose a region near the restaurant — Singapore for Pakistan).
2. Database Access → add a user with read/write on the database. Use a long generated password.
3. Network Access → Render does not publish stable egress IPs, so allow `0.0.0.0/0`. The cluster is
   reachable only with that database user's credentials, which is why the password matters.
4. Connect → Driver → copy the SRV string, and append the POS's own database name:
   `mongodb+srv://<user>:<password>@<cluster>/food_pos?retryWrites=true&w=majority`
5. Create the `food_pos` database (an empty one is fine; collections are created on first write).

## 2. Render

1. Push this repository to GitHub, then Render → **New → Blueprint** and pick it. `render.yaml`
   declares the service, so the form is mostly pre-filled.
2. Set `MONGODB_URI` to the SRV string. `JWT_SECRET` is generated by Render on first deploy and
   reused afterwards; leave every other value as declared:
   - `NODE_ENV=production` — without it the server accepts a missing `MONGODB_URI` and starts an
     in-memory database, i.e. it silently forgets every order.
   - `AUTO_SEED=false` — seeding creates demo staff, which must never appear on a public host.
   - `CORS_ORIGIN` — deliberately unset. The SPA and the API share one origin, and the server
     already allows a request whose `Origin` host equals its own `Host`.
   - `UPLOAD_DIR` — deliberately unset, so menu photos land in `backend/uploads`, which is where
     the 1 GB persistent disk is mounted.
   - `plan: 0.5c-512mb` — persistent disks need a paid instance, and Render's free instances sleep
     after inactivity, which a register cannot afford.
3. Deploy. The build runs `cd frontend && npm ci && npm run build && cd ../backend && npm ci --omit=dev`,
   then starts `node backend/src/server.js`.
4. Check `https://<service>.onrender.com/health` returns `{"status":"ok"}`.

`mongodb-memory-server` is a devDependency and is imported lazily, so a production install never
downloads a MongoDB binary during the build.

## 3. First staff unlock

The POS unlocks with a staff PIN (`POS_PIN`, default `12345`) at `/login`. The login endpoint still
needs at least one staff user in MongoDB so it can issue a JWT — create one if the database is empty:

```sh
BOOTSTRAP_EMAIL=owner@example.com BOOTSTRAP_PASSWORD='a long password' npm run staff:create
```

Set `POS_PIN` in the service environment to change the unlock code. Re-running `staff:create` with
an existing email resets that user's password (used only for bootstrap / recovery scripts).

## 4. Menu and table QR codes

Either import the live data from the website's Postgres
([backend/README.md](../backend/README.md#importing-the-old-website-data-one-off)) or add categories,
products and the three floor tables through the POS pages. Then print the guest links for the
tables — `https://<service>.onrender.com/t/1`, `/t/2`, `/t/3` — and each table's menu opens against
this POS, with orders arriving in Online Orders.

## 5. After the first deploy

- **Backups**: Atlas M0 has no automated backup; take an ad-hoc snapshot before importing data.
- **Re-deploys**: pushing to the tracked branch re-runs the same build; the disk and the Atlas
  database survive it.
- **Domain**: point a custom domain at the service if the printed QR codes should not change when
  the Render name does. QR links already printed carry the old host, so decide the URL once.
- **Logs**: Render → Service → Logs; `GET /health` is the readiness probe, so a database that
  cannot be reached shows up as a failing deploy rather than a broken register.
